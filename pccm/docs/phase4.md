# PCCM — Phase 4: Structural Runtime

**Status: Gate A (source) complete, pending review. Gate B (Windows runtime) not started.**

Phase 4 is the first phase with Stage-B behaviour. It introduces the applied
timeline, permanent identity, the profiling and inflation grids, the Add/Delete
driver operations and the Stage-B build path.

It is **structure only**. No cost, risk, escalation, FX, NPV, EMV, simulation,
RNG, Model Check, sensitivity, results or dashboard logic exists.

Authority for functional design remains the **Architecture Lock, Revision B**.
Phases 1–3 are closed.

### Nothing is restated in another language

VBA and PowerShell cannot read YAML, so the Stage-A build **projects** the
contract into both:

    build/vba/modConstants.bas    every structural literal the VBA needs
    build/stage_b_manifest.json   every structural literal the PowerShell needs

The bootstrap reads sheet names, CodeNames, module names, button captions and
macro names from the manifest. The harness reads expected years from the fixture.
Neither hard-codes any of them, and tests assert that: `test_34` fails if a
CodeName or entry point appears literally in the bootstrap, and `test_38` fails
if a calendar-year literal appears anywhere in the harness.

## Entered vs applied timeline

The **entered** triple is the accepted Phase-2 Setup inputs. Phase 4 does not
move, rename or re-own them — `inpBaseYear`, `inpProjectStartYear` and
`inpDurationYears` are unchanged and still valid.

Structural VBA needs a stable canonical name rather than a hardcoded Setup
coordinate, so the contract declares **aliases over the same cells**:

| Alias | Aliases | Cell |
|---|---|---|
| `nmBaseYear_Entered` | `inpBaseYear` | `Setup!C12` |
| `nmStartYear_Entered` | `inpProjectStartYear` | `Setup!C11` |
| `nmDuration_Entered` | `inpDurationYears` | `Setup!C10` |

The loader asserts each alias resolves to *exactly* the reference its `inp*` name
resolves to, so there is one semantic source for each entered value and never a
second copy.

The **applied** triple is separate, model-controlled state, plus four derived
structural names:

| Name | Cell | Kind |
|---|---|---|
| `nmBaseYear_Applied` | `Setup!C46` | written by Apply only |
| `nmStartYear_Applied` | `Setup!C47` | written by Apply only |
| `nmDuration_Applied` | `Setup!C48` | written by Apply only |
| `nmLastYear_Applied` | `Setup!C50` | derived: Start + Duration − 1 |
| `nmYearCount_Applied` | `Setup!C51` | derived: the generated column count |
| `nmInflFirstYear` | `Setup!C53` | derived: Base + 1 |
| `nmInflLastYear` | `Setup!C54` | derived: equals last project year |

The derived four are **formulas**, not stored values, so they cannot go stale
against the applied triple.

Entered values have **no structural effect** until Apply succeeds. Every grid and
every later calculation phase binds to the applied triple.

### Initial state

On a new workbook the entered triple is blank, the applied triple is blank, no
year column exists in any grid, and each grid displays

> Timeline not yet applied. Project-year columns are generated by Apply / Update Timeline on Setup.

No year is fabricated. Permanent IDs can still be allocated before a timeline
exists; those rows simply carry the fixed columns and no year cells.

## Structure Change Pending

`nmStructuralState` on `Setup!C41` is a **worksheet formula**, deliberately not a
`Worksheet_Change` handler: the flag must update the instant an entered value is
edited, and an event handler would make structural state depend on hidden
automation. Section 27 of the phase scope forbids exactly that shortcut.

Three states, because two would be dishonest:

| State | When |
|---|---|
| `No timeline applied` | the applied triple is blank and nothing has been entered |
| `STRUCTURE CHANGE PENDING` | any entered value differs from its applied counterpart |
| `Timeline current` | all three match |

A brand-new workbook has blank == blank in all three positions. Reporting that as
"current" would claim a timeline is in force when none is. The loader asserts
every entered and applied name appears in the formula, and that each declared
label literal actually appears in it.

## Apply / Update Timeline

One pathway. There is no second structural state machine: profiling row sync,
inflation profile sync and year-column generation all run from here, because
splitting them would allow a state where one grid was synchronised and another
was not.

    1. PREVALIDATE   the entered triple. Nothing is touched until it passes.
    2. ASSESS        the combined old → new delta and what it would destroy.
    3. CONFIRM       before modifying anything.
    4. SNAPSHOT      the blocks this operation may modify.
    5. APPLY         then REVALIDATE, and RESTORE those blocks on any failure.

### Prevalidation

Rejects, without touching applied state, and reporting **every** failure at once:

- any of the three not a whole number
- Duration < 1
- Base Year or Start Year outside 1900–2200
- Base Year > Start Year
- Last Project Year beyond the supported structural year boundary
- generated project-year columns beyond the structural protection limit

**25 years is not a cap.** It is an Architecture benchmark target; a 40-year
project is a legitimate model and `test_12` asserts durations of 26, 40, 75 and
120 all pass. The only width guard is `max_generated_year_columns`, and that is
not an independent invented number either — the loader asserts it equals
`max_year − min_year + 1`, the width of the supported calendar-year window. A
guard derived from the year boundary cannot drift away from it.

### One combined delta

Base Year, Start Year and Duration may all change before Apply. The operation
computes **one** old configuration and **one** new configuration, and applies the
difference as a single transition.

Three sequential partial transitions would be wrong twice over: the workbook would
expose half-applied structural states, and the destructive assessment would
over-report. `test_29` demonstrates the second: shrinking 4 → 2 and growing back
to 4 destroys two project years, while the combined delta with duration unchanged
at 4 destroys nothing.

## Applied year semantics

    Last Project Year = Applied Start Year + Applied Duration − 1

The two grids use **different anchors**, and everything in Phase 4 turns on the
difference.

### Profiling — anchored by PROJECT-YEAR INDEX

A profiling percentage means "this share falls in project year *N*", not "this
share falls in 2029".

| Change | Effect |
|---|---|
| Start Year moves, Duration unchanged | headers relabel; **no value moves** |
| Duration increases | new cells **appended at 0%**; every existing value unchanged |
| Duration decreases | cells removed **from the tail only** |
| Base Year changes | profiling is **untouched** |

A row that totalled 100% before a duration increase still totals 100% after it.
There is no redistribution, no normalisation, and no formula pretending a row is
valid. The 100% requirement is a Model Check rule.

### Inflation — anchored by CALENDAR YEAR

A rate entered against 2029 stays attached to 2029 for as long as 2029 is inside
the required span, whatever column index it lands in. A rate is **never** shifted
because its column position changed.

Required span: `Applied Base Year + 1` through `Applied Last Project Year`.

| Change | Effect |
|---|---|
| Start Year moves | years leave one end and arrive at the other; survivors keep their rates |
| Base Year earlier | earlier years arrive **blank** |
| Base Year later | early years leave the span |
| Duration increases | later years arrive **blank** |

**A newly required year is BLANK, never 0%.** Seeding zero would fabricate an
escalation assumption the user never made and would hide a missing rate from the
Model Check phase that is meant to block on it. The contract rejects a non-null
`initial_value` on the inflation year column, and rejects a null one on the
profiling year columns — the two are deliberately different and both load-bearing.

### The degenerate span is legitimate

When Base Year = Start Year and Duration = 1 there is no year between the price
base and the end of the project, so **no** escalation assumption is required. The
grid keeps its fixed column, creates no year column, and shows:

> No inflation years are required for the applied timeline. This is legitimate when Base Year = Start Year and Duration = 1.

It is never left as a zero-width or malformed table.

## Destructive change

Assessment runs **before** anything is modified, which is why **cancellation
needs no rollback**: nothing has moved when the user is asked. `test_32` asserts
the assessment function is pure.

A change is destructive only when real user data would be lost. Removing 0%
profiling cells or blank inflation cells destroys nothing and gets the ordinary
structural confirmation.

The destructive prompt names:

- the old and new timeline
- which project years are removed
- the count of non-zero profiling percentages affected
- representative affected permanent IDs
- that the data will be permanently deleted

## Permanent identity

| Register | Format | Counter |
|---|---|---|
| Cost Lines | `CL-001`, `CL-002`, … | `nmCounterCostLine` on `_Calc!C10` |
| Risk Register | `R-001`, `R-002`, … | `nmCounterRisk` on `_Calc!C11` |

Rules, all load-bearing:

- An identifier comes from the **persistent counter** and nowhere else. Never from
  a row number, never from a row count.
- Deletion **never** decrements the counter. Add, Add, Add, delete `CL-002`, Add
  yields **`CL-004`**. `CL-002` is never reused.
- Pad width is a **minimum display width**, not a range limit. `CL-999` is
  followed by `CL-1000`. The contract rejects a pattern that would refuse a
  four-digit sequence.
- The two sequences are independent; the contract rejects a shared prefix or two
  counters claiming one register.
- Reordering the register moves rows, not identity: the ID lives in the row and
  travels with its own data.

Structural revalidation checks **counter ≥ highest issued**, never
*counter == row count*: after a deletion the counter is deliberately ahead of the
count, and counting rows instead of reading the counter would reissue an
identifier (`test_38`).

## Add / Delete driver

**Add** allocates the next ID, uses the first genuinely blank reserved row, grows
the table if none is free, writes **only** the model-controlled ID, synchronises
the profiling row, initialises that driver's project-year cells to 0% if a
timeline is applied, selects the first field the user owns, and persists the
advanced counter.

Reserved rows are **not** pre-numbered. And a row that already holds user content
but carries no ID is an **orphan**, not free space: Add refuses it and explains
the condition rather than silently taking ownership of somebody's typing. A
repair tool is a Phase-10 question.

**Delete** operates only on an identified row, shows a confirmation naming the ID,
the description or risk name, and the matching profiling row deletion, then
**re-resolves the row by identity after confirmation** — a row that moved during
the prompt cannot cause the wrong driver to be deleted. `test_23` asserts that
second resolution exists.

---

## Profiling synchronisation

Invariant: for every non-blank Cost Line ID exactly one Cost Profiling row, and
for every non-blank Risk ID exactly one Risk Profiling row. No duplicates. No row
for a deleted driver.

Percentages are preserved by **permanent ID + project-year index**, never by
worksheet row, so a driver-table reorder reorders the grid and transfers nothing
between rows.

---

## Logical rollback

A user cancellation occurs before modification and needs no rollback.

For a genuine mid-operation runtime error, the operation captures only the blocks
it may modify — the applied triple, the two profiling grids, the inflation grid,
and for Add/Delete the driver row and counter state — and restores those values
and shapes on failure, restores application state, reports the failure clearly,
and runs structural revalidation.

There is deliberately **no** generic transaction framework, **no** undo journal
and **no** workbook snapshot system. Logical restoration is the requirement.

The counter is restored **only** on a failed operation, which issued no surviving
identifier. A successful delete never restores it.

## Structural revalidation

`modStructuralCheck` is a focused Phase-4 gate, **not** the Model Check engine. It
has no severities, no register, no overall status and no simulation gate. It
**reports** and never repairs — `test_20` asserts the module writes nothing to the
workbook. A failure makes the macro operation fail.

Checks: applied triple internally consistent; profiling column count equals
Applied Duration; profiling headers run Start→Last with no gap; Cost and Risk
profiling IDs match their registers 1:1; no duplicate IDs; IDs match their
declared prefix and pattern; inflation headers match the required span exactly;
inflation rows match the Config profile names; counters not behind their highest
issued ID; no malformed grid state.

It checks nothing about business validity: a row that does not total 100%, a
missing inflation rate and a blank unit cost all pass here.

## Structural formulas

Phases 1–3 prohibited every formula. Phase 4 permits **structural-state display
only**, and the permitted cells are enumerated by the contract
(`StructureContract.formula_cells`): the four derived timeline cells, the state
indicator, and one message cell per grid.

The old zero-formula tests were made **phase-aware, not deleted**. They still fail
on any formula outside that enumerated set, so a business calculation would trip
them exactly as before.

## Stage-B build path

    python3 pccm/builder/build_stage_a.py            # Linux: .xlsx + generated inputs
    .\bootstrap\windows\build_stage_b.ps1            # Windows: .xlsx -> .xlsm
    .\bootstrap\windows\phase4_functional_test.ps1   # Windows: functional matrix A-L

The bootstrap opens an owned Excel instance, saves as `.xlsm` (FileFormat 52),
applies the 14 locked CodeNames, imports the VBA, creates the five buttons with
`OnAction`, saves, closes, releases COM in explicit named order, then **reopens in
a fresh instance** and verifies what actually persisted.

It changes no security setting, and the COM lifecycle policy is the one proven by
the Phase-1.6 readiness gate, implemented once in `com_lifecycle.ps1` and
dot-sourced by both scripts. See `bootstrap/windows/README.md`.

## Deliberately not implemented

- Deterministic cost and impact calculations; distribution expectations; FX
  conversion; escalation; NPV; Expected Risk / EMV
- Monte Carlo, RNG, sensitivity, results statistics
- Model Check framework; stale-result fingerprint; Run Stamp
- Dashboard calculations and charts
- Worksheet protection lockdown
- Class modules and document modules
- Any input `Worksheet_Change` automation

## Known limitations

1. **The Windows runtime is unproven.** The Linux tests establish that the rules
   are coherent and that the source is internally consistent. They cannot execute
   VBA. Only Gate B closes this.
2. **The structural protection limit is derived, not quoted.** It is the width of
   the supported calendar-year window (301). If Revision B fixes a different
   figure, it is a one-line contract change.
3. **Profiling year cells carry no data validation.** A per-cell bound would block
   ordinary partial entry, and the 100% requirement is a Model Check rule.
4. **Trace columns are refreshed, not live.** Description and Risk Name are copied
   into the profiling grids by synchronisation; editing the register updates them
   at the next structural operation, not instantly.
5. **`lst*` ranges remain fixed-size**, carried from Phase 2.
6. **Nothing consumes the applied timeline yet.** No calculation reads it; the
   grids exist so later phases bind to a stable structure.
